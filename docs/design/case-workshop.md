# 设计方案：用例工坊 + 需求覆盖矩阵

> 状态：M1～M4 已实现（2026-11-02）。第 8 节的真实数据还没有采集。
>
> 与本方案的差异：
> - 需求文档不按版本存多行，而是一行 + `version` 字段；解析记录里保存解析时的版本号，原文更新后页面提示重新解析。
> - “试运行草稿”没有做：运行记录依赖正式用例（`runs.case_id`），改为入库后在批次页“运行本批入库用例”，用首次运行结果算“生成即跑通率”。
> - 用例列表 / 编辑页显示关联需求点、首页覆盖率卡片暂未做。
> - 目前只有 `gen-v1`。`gen-v2` 要根据 v1 的真实废弃原因来写，不提前编。
> 一句话：现在的 AI 生成是“生成完就结束了”；这次把它做成**可审核、可度量、可追溯**的流水线，并且回答两个问题——“AI 生成的用例到底有多少能用”和“需求测全了没有”。

## 1. 背景与目标

### 现状
`/api/generate` 输入一段需求文字，返回若干条用例草稿（Midscene 自然语言步骤），用户在 Generate 页勾选后入库。问题：
- 没有记录：用了哪个模型、哪版 Prompt、输入是什么，生成结果事后无法追溯；
- 没有度量：多少条被直接采纳、多少要改、多少被丢弃、为什么丢弃，都不知道；
- 没有追溯：入库后的用例和需求没有关系，看不出哪些需求还没测。

### 参考了什么
| 来源 | 借鉴 | 不借鉴 |
|---|---|---|
| 小红书“宇宙AI测试”平台 | AI 只起草、人工逐条审核才入库；按批次看覆盖率提升 | 一次输入生成接口 / 压测 / App 全流程（展示型，做不深） |
| TestHub（GitHub 863★） | 用例评审流程、评审状态跟踪 | 多人评审、权限（个人项目用不上） |
| WHartTest（GitHub 1.1k★） | 生成策略 / Prompt 模板可配置、显示 Token 用量 | LangGraph + 向量知识库（太重，1GB 服务器跑不动） |
| SoftJL（GitHub 133★） | 需求点标明原文出处；**“关联了用例 ≠ 测试通过”** | UML / 文档生成 |

### 目标
1. **用例工坊**：需求文档 → 需求点 → 按批次生成 → 逐条审核 → 入库，全程留痕。
2. **度量**：采纳率、修改率、废弃原因分布、入库后首次运行通过率；能对比 Prompt 版本。
3. **需求覆盖矩阵**：每个需求点的覆盖状态，区分“已关联”和“已执行通过”；对缺口定向补生成。

### 不做
需求变更自动对比（放到后续）、向量知识库、多人协作、压测 / App 自动化。

### 和别的平台不一样的地方
- **生成的用例能直接执行**：TestHub 等生成的是“前置条件 / 步骤 / 预期”文本用例，要人再写脚本；这里生成的是 Midscene 步骤，入库就能跑，还能统计“生成即跑通率”。
- **把“AI 生成好不好”当成评测问题**：不只说“AI 生成”，而是给出采纳率、置信区间和 Prompt 版本对比，方法沿用字幕翻译评测项目。

## 2. 流程

```
需求文档（粘贴文本 / 上传 .md .txt）
   │  ① 解析（LLM）：拆成需求点，每点带编号、优先级、原文摘录
   ▼
需求点（人工可增删改，确认后才能生成）
   │  ② 生成批次（LLM）：选范围（全部 / 未覆盖 / 勾选的点）+ Prompt 版本
   ▼
草稿（draft，不是正式用例，不计入覆盖）
   │  ③ 审核：通过 / 修改后通过 / 废弃（必选原因）
   ▼
正式用例（cases 表，带“关联需求点”和“来源草稿”）
   │  ④ 执行（已有能力）
   ▼
覆盖矩阵：需求点 × 用例 × 最近运行结果
```

规则：
- **AI 只起草**：草稿不进用例列表、不计入覆盖率，只有人工判定后才入库。
- **每一步都留痕**：解析和批次记录模型、Prompt 版本、输入哈希、Token、耗时；审核记录原稿与终稿。
- **可以多次解析、多次生成**：需求文档改了就重新解析；覆盖不够就针对缺口再生成一批。

## 3. 数据模型

新增 6 张表，现有 `cases` 加 2 列。沿用现在的写法：JSON 存在 TEXT 列，`migrate()` 中按需补列。

```sql
-- 需求文档（一个文档可以有多个版本，每次修改内容就是新的一行）
requirements (
  id, name, version,          -- 如 “订单中心 PRD”, 2
  content TEXT, content_hash, -- 原文与 sha256，用于判断“同一输入”
  target_url,                 -- 生成用例时的默认 URL，如 {{DEMO}}/index.html
  created_at
)

-- 一次解析（需求文档 → 需求点）
parses (
  id, requirement_id, model, prompt_version,
  tokens, duration_ms, raw_output TEXT,  -- 保留模型原始输出，便于排查
  created_at
)

-- 需求点
req_points (
  id, requirement_id, parse_id,      -- parse_id 为空表示人工新增
  code,                              -- REQ-001，同一文档内唯一
  title, detail, priority,           -- P0 / P1 / P2
  source_excerpt,                    -- 原文摘录（出处），防止模型凭空编需求
  status,                            -- active / removed（人工删除时软删）
  created_at, updated_at
)

-- 一次生成
gen_batches (
  id, requirement_id, parse_id,
  scope TEXT,                        -- JSON: 本批针对的需求点 id[]
  model, prompt_version, input_hash, -- input_hash = 需求点内容 + prompt 版本，相同输入可比
  tokens, duration_ms, raw_output TEXT,
  created_at
)

-- 草稿（一条 = 模型生成的一条用例）
drafts (
  id, batch_id,
  name, description, url, steps TEXT,   -- 原稿，生成后不再修改
  point_ids TEXT,                       -- JSON: 模型声称覆盖的需求点 id[]
  confidence REAL,                      -- 模型自评 0~1，用于排序；可为空
  verdict,                              -- pending / accepted / edited / discarded
  discard_reason,                       -- 见 4.3
  final TEXT,                           -- JSON: 审核后的终稿（edited 时与原稿不同）
  edit_stats TEXT,                      -- JSON: 步骤增 / 删 / 改的数量
  note, reviewed_at,
  case_id                               -- 入库后的用例 id
)

-- 用例 ↔ 需求点（多对多）
case_points (case_id, point_id, PRIMARY KEY (case_id, point_id))

-- cases 加两列
ALTER TABLE cases ADD COLUMN source_draft_id INTEGER;   -- 来自哪条草稿，手写用例为空
ALTER TABLE cases ADD COLUMN requirement_id INTEGER;
```

说明：
- 需求点用编号（`REQ-001`）对外展示，重新解析时尽量沿用旧编号（按标题相似度匹配），这样覆盖矩阵不会因为重新解析整体错乱。
- 草稿原稿不可修改，终稿另存：这是计算“修改率”的依据，也能回答“AI 原来写的是什么、人改了什么”。

## 4. 功能设计

### 4.1 需求与解析
- 新建需求：名称、目标 URL、原文（粘贴或上传 .md / .txt，≤ 20000 字）。
- 点“解析”调用模型，返回需求点列表；**每个需求点必须带原文摘录**，摘录在原文里找不到的（模型编造）标红提示。
- 解析结果可人工编辑：改标题和优先级、合并、删除、手工新增。
- Prompt：`server/ai/prompts/parse-v1.md`。

### 4.2 生成批次
- 选范围：全部需求点 / 只选未覆盖的 / 手动勾选。
- 选 Prompt 版本：`server/ai/prompts/gen-v1.md`、`gen-v2.md`……文件名就是版本号，**改 Prompt 必须新建版本文件，不能原地修改**，否则历史数据不可比。
- 输出要求：每条用例写明覆盖哪些需求点（`point_ids`），并自评置信度。
- 和现有 `parseDrafts` 一样做格式校验：不合规的步骤丢弃，`point_ids` 里不存在的 id 丢弃。
- 生成是同步调用（现有 `/api/generate` 就是同步的），超时沿用 `MIDSCENE_MODEL_TIMEOUT`。

### 4.3 审核工作台（核心页面）
布局参考 Trace Viewer 式运行详情：左侧审核队列，右侧当前草稿。

- 队列默认按置信度**从低到高**排，先看最可能有问题的。
- 右侧展示：用例名、描述、关联需求点（可改）、步骤（复用现有 `StepsEditor`）。
- 三种判定，支持快捷键：
  - `A` 通过：原样入库；
  - `E` 修改：进入编辑，保存后按“修改后通过”入库，自动统计步骤增 / 删 / 改；
  - `D` 废弃：必须选原因。
- **废弃原因**（固定枚举，便于统计）：
  | 原因 | 含义 |
  |---|---|
  | `duplicate` 重复 | 与已有用例或同批其他草稿重复 |
  | `out_of_scope` 需求外 | 测的东西需求里没有（幻觉） |
  | `not_executable` 不可执行 | 步骤依赖不存在的元素 / 数据，或顺序不对 |
  | `vague_assert` 断言含糊 | 如“操作成功”，无法判断 |
  | `low_value` 价值低 | 正确但没必要 |
  | `other` 其他 | 必须填备注 |
- 可选“试运行”：对当前草稿直接执行一次（复用执行器，结果不计入用例历史），帮助判断能不能跑通。
- 审核完的草稿入库，写 `case_points`，在批次页显示进度。

### 4.4 度量（批次页 + 对比页）
口径写清楚，页面上鼠标悬停可以看到定义：

| 指标 | 定义 |
|---|---|
| 采纳率 | (通过 + 修改后通过) / 已审核 |
| 直接采纳率 | 通过 / 已审核 |
| 修改量 | 修改后通过的草稿，平均每条改了几步 |
| 废弃原因分布 | 各原因占比 |
| 生成即跑通率 | 入库用例**首次运行**的通过率（只算这一批生成的用例） |
| 新增覆盖 | 这一批让多少个需求点从“未覆盖”变成“已关联” |
| 成本 | Token、耗时，以及“每条被采纳用例的 Token” |

**Prompt 版本对比**：同一份需求、相同需求点、不同 Prompt 版本各生成一批，并排展示上面的指标。
- 每批样本量通常只有二三十条，所以采纳率同时给出 **95% 置信区间**（Wilson 区间），两版差异给出 Fisher 精确检验的 p 值；
- 样本太少（如每组 < 20）时页面直接提示“样本量不足，结论仅供参考”，不夸大结论。

### 4.5 需求覆盖矩阵
每个需求点一行，状态按以下规则计算（**关联 ≠ 通过**）：

| 状态 | 条件 |
|---|---|
| 未覆盖 | 没有关联任何正式用例 |
| 已关联·未执行 | 关联了用例，但都还没跑过 |
| 已验证 | 至少一条关联用例的最近一次运行通过 |
| 失败 | 关联用例最近一次运行都失败 |

页面内容：
- 概览：需求点总数、各状态数量、**P0 未覆盖**告警；
- 按批次看覆盖率变化：`batch-1 后 45% → batch-2 后 70%`；
- 矩阵表：需求点 / 优先级 / 关联用例 / 最近运行结果 / 操作；
- 对未覆盖的点：勾选后“只针对这些生成”，即以它们为范围新建一个批次（回到 4.2）；
- 导出 CSV。

### 4.6 和现有功能的关系
- 现有 Generate 页保留，作为“快速生成”（不建需求、不留批次），入口文案说明区别。
- 用例列表、用例编辑页显示“关联需求点”和“来源：批次 #n”，可跳回需求。
- 首页概览加一张卡片：需求覆盖率、待审核草稿数。
- 访客只读模式：可以查看需求、批次、度量和矩阵；解析、生成、审核需要管理员（沿用 `access.ts`，相关路由加入只读拦截）。

## 5. 接口

```
POST   /api/requirements                    新建需求（含原文）
GET    /api/requirements                    列表（含覆盖率摘要）
GET    /api/requirements/:id                详情（需求点、批次列表）
POST   /api/requirements/:id/parse          解析 → 返回 parse 与需求点
PUT    /api/requirements/:id/points         批量保存人工编辑后的需求点
POST   /api/requirements/:id/batches        生成批次 {scope, promptVersion}
GET    /api/batches/gen/:id                 批次详情 + 草稿 + 度量
POST   /api/drafts/:id/verdict              审核 {verdict, final?, reason?, note?, pointIds?}
POST   /api/drafts/:id/try-run              试运行
GET    /api/requirements/:id/coverage       覆盖矩阵
GET    /api/requirements/:id/coverage.csv   导出
GET    /api/requirements/:id/compare?batches=1,2   Prompt 版本对比
GET    /api/prompts                         可用 Prompt 版本列表
```

## 7. 测试

沿用现有三层：
- **单元测试（vitest）**：解析与生成输出的校验（缺字段、不存在的需求点 id、摘录找不到）、指标计算（含边界：0 条已审核、全部废弃）、Wilson 区间与 Fisher 检验对照已知数值、覆盖状态判定、编号沿用匹配。模型调用用现有的 `fetchImpl` 注入假响应。
- **接口测试（pytest）**：完整链路（建需求 → 解析 → 生成 → 审核 → 覆盖矩阵）；校验（废弃不选原因 400、对已审核草稿重复审核 409、访客调用 403）；JSON Schema 契约。
- **E2E（Playwright）**：审核工作台的快捷键流程、覆盖矩阵“补生成”闭环。用本地假模型（现有 E2E 已有）。

## 8. 真实数据计划（写进简历的数字从这里来）

1. **输入**：两份真实需求。
   - 毕设“在线考试智能监考系统”的需求（取自你论文里的需求分析章节，由你提供文本；不读毕设项目里的任何配置或密钥文件）；
   - 平台自带演示站点 TodoLite 的需求（现有 Generate 页里的示例）。
2. **生成**：每份需求用 `gen-v1` 和 `gen-v2` 各生成一批。v2 根据 v1 的废弃原因来改，例如 v1 断言含糊多，v2 就加断言写法的约束和示例。
3. **审核**：由你本人逐条审核，约 4 批 × 20～30 条，大约一小时。
4. **执行**：入库后跑一次，得到“生成即跑通率”；TodoLite 的用例在演示站上跑，监考系统的用例在本机跑。
5. **记录**：数字全部来自平台导出，写进 `docs/workshop-results.md`，注明日期、模型、样本量。**结果不理想就如实写**，比如“v2 采纳率提高但置信区间重叠，差异不显著”。

简历可能的写法（数字待实测后填写）：
> 设计 AI 用例生成的审核与度量流程：需求解析为带出处的需求点 → 按批次生成 → 逐条审核留痕；以采纳率、废弃原因、生成即跑通率评估生成质量，对比 Prompt 版本（采纳率 x% → y%，n = …）；需求覆盖矩阵区分“已关联”和“已验证”，对缺口定向补生成。

## 10. 后续（这次不做）
- **需求变更影响**：需求新版本重新解析后，对比需求点，变化的点把关联用例标为“待复核”。
- **AI 失败归因**：运行失败时让模型把原因归到“产品缺陷 / 定位失效 / 时序问题 / 环境问题”，用你在爱奇艺整理的真实失败根因作为标注数据，计算准确率。
- **只读 MCP 服务**：让 Claude Code / Cursor 查询需求覆盖与运行结果。
