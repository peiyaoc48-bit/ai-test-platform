# 探索模式与 UI 知识库：设计方案（草案 v2）

> 状态：M1 已实现（2026-11-06），M2 起待实现｜提出：2026-11-04｜作者：陈培瑶（构想）、总控助理（整理）、对照现有代码修订（2026-11-04）
>
> v2 的改动见第 7 节“审阅记录”。主要变化：安全边界加了一道网络层拦截，不再只靠关键词；稳定性检查改用变更注入，不再在同一页面上重复定位 3 次；选择器兜底复用现有的“代码步骤 + AI 兜底”结构；第一版不做向量检索；评估实验在动手前先写清楚预期，并说明疑难控件是作者自己加进演示站的。

## 1. 要解决的问题

在 AI UI 自动化（Midscene 视觉定位）的实践中，有一类问题反复出现：

- **纯图标控件认不出或认错**：例如播放按钮（三角形）、收藏、倍速等，视觉模型经常定位失败；
- **自然语言描述写不准**：测试同学不知道该怎么描述，Midscene 才能稳定执行；
- **新接手一个系统时，从零了解功能和业务很慢**：用例要等熟悉了业务才能写。

目前的补救办法是人工维护“知识库”：用 PO 封装疑难控件和常用步骤，告诉 AI 要做什么。这个办法有效，但**全靠人工积累**。

**目标**：让 Agent **自己探索**一个新系统，自动构建三样东西：
1. **控件知识库**：每个控件是什么、在哪、怎么定位，以及 Midscene 能稳定执行的描述；
2. **状态转移图**：在哪个页面做什么动作，会到达什么状态。这相当于该系统的“世界模型”；
3. **业务流程地图**：从转移图里归纳出“登录 → 搜索 → 播放”这类核心路径。

在此基础上，**用例编写傻瓜化**：用户说“测一下未登录用户点击 VIP 视频”，平台查询知识库和转移图，生成 Midscene 能执行的步骤；疑难控件自动退回到选择器。

## 2. 相关工作（写进 README 和面试讲稿时引用）

| 工作 | 做法 | 与本方案的关系 |
|---|---|---|
| Crawljax（Web）、DroidBot（Android） | 自动遍历 GUI，建立状态流图，用于基于模型的测试 | 状态转移图的经典做法；状态等价判断、回放到某状态的方法都参考它们 |
| AppAgent（腾讯，2023） | 先让 Agent 探索 App，把控件功能写成文档，执行任务时查阅 | 与“控件知识库”思路一致 |
| AutoDroid（MobiCom 2024） | 随机探索得到 UI 转移图，再由大模型提炼为任务记忆并检索使用 | 与“转移图 + 检索”思路一致 |

本方案的区别：面向 **Web 测试平台**，与 Midscene / Playwright 用例直接打通；每个知识点都经过“点一下验证”；并用对照实验量化收益。引用前要核对论文的标题、作者和年份，不凭记忆写。

## 3. 总体流程

```
① 探索              ② 标注与验证                      ③ 沉淀                 ④ 使用
Playwright 遍历 →  截图 + 可访问性树 + DOM 摘要    →  控件知识库        →  用例生成 / 执行时注入
(BFS，限深限次)     大模型标注控件功能                 状态转移图            Midscene 加背景描述
网络层拦截写请求    点击验证：对比前后状态               业务流程地图          疑难控件 → 代码步骤 + AI 兜底
                    变更注入下检查定位稳定性
                    人工审核（可选）
```

### 3.1 探索器（Explorer）

- **起点**：基础 URL，加可选的预置登录态（复用“环境”配置里的地址、变量和登录态；登录用的口令只从环境变量读取，不写进探索记录）；
- **遍历策略**：广度优先；最大深度、最大状态数、最大点击数可配置。M1 不调用模型，所以没有 token 上限；从 M2 开始加；
- **回到某个状态**：广度优先要反复回到之前的状态。做法是从起点重放到达该状态的动作路径（Crawljax 的做法），不依赖浏览器的后退。回放后再算一次指纹，和记录不一致就记为“状态不可复现”，不再从它往下探索；
- **状态去重**：状态 = URL 模板 + 可交互元素“结构”的指纹：
  - URL 模板：把路径里的数字段和长 id 替换成占位符（`/videos/123` → `/videos/:id`），查询参数只保留键名；
  - 元素结构：取可交互元素的 role 和可访问名称，**同一父元素下重复出现的兄弟元素合并成一条**（列表项、待办条目、视频卡片），名称里的数字归一化。否则列表多一条数据就会变成新状态，状态数量会爆炸；
- **候选动作**：从可访问性树中取可交互元素（button / link / textbox / tab / checkbox，以及带 aria-label 或 title 的纯图标元素）；同一组重复元素只试第一个。输入框用固定的测试文本填写（例如“探索测试 001”）。

### 3.2 安全边界（必须实现，M1 的验收重点）

只靠“认出危险按钮”是不够的：关键词会漏掉，大模型也会判断错。所以分两层，第二层不依赖识别是否准确：

1. **识别层（不点）**：按钮或链接的名称命中危险关键词（删除、移除、注销、退出、支付、购买、下单、提交订单、修改密码、重置、清空……，中英文都有），或者 M2 以后被大模型判为危险的，**只记录、不点击**，标记为“需人工确认”。退出登录也算：它对被测系统无害，但会让探索丢掉登录态；
2. **拦截层（点了也发不出去）**：探索时用 `page.route` 拦截全部请求：
   - 目标域名不在白名单里的，导航和请求都取消（不跟随跳出白名单的链接，第三方脚本也不加载）；
   - 非 GET 请求（POST / PUT / PATCH / DELETE）默认一律取消，只放行配置里明确列出的接口（例如登录接口）。被取消的请求记入探索记录，说明“这个动作会写数据”。这本身也是有用的知识；
3. **其他**：只用测试账号和测试环境；每次点击后至少等待一段时间（可配置），控制请求频率；探索和用例运行共用同一个执行队列，同一时间只开一个浏览器（演示站只有 1 核 1GB，systemd 限制 MemoryMax=800M）；
4. **探索记录不保存敏感信息**：仓库里**目前没有通用的脱敏逻辑**（v1 草案说“复用”是错的）。M1 新增：输入框类型为 password 的值不记录；请求头里的 Authorization 和 Cookie 不记录；预置登录态只存引用，不存内容；
5. **权限**：只读访客不能发起探索，也不能修改知识库（沿用现有的 access 规则，非 GET 接口一律 403），并补测试证明。

**M1 的测试**：新建一个测试夹具页面（放在 tests/fixtures，不放进演示站），上面有“删除”“支付”“退出登录”按钮、一个名字普通但会发 POST 请求的按钮、一个跳到白名单外的链接。断言：
- 前三个按钮的点击计数为 0；
- 那个普通名字的按钮被点了，但它的 POST 请求被取消，服务端收到的写请求数为 0；
- 白名单外的地址一次都没有被请求；
- 探索在设定的上限内结束，同一列表多几条数据时状态数不变。

### 3.3 标注与验证（M2）

对每个候选控件：
1. **标注**：把截图（框出元素）、可访问性信息和周围文字交给视觉模型，输出 `功能描述`、`Midscene 描述`（例如“视频画面中央的白色三角形播放按钮”）、`元素类型`；
2. **验证**：执行点击（仍在 3.2 的拦截层之下），对比前后的状态指纹、URL、新出现或消失的元素，判断“实际效果”是否与标注一致；
3. **定位稳定性检查**：v1 草案的“同一页面调用 `aiLocate` 3 次”测不出问题。Midscene 开启缓存时，后两次直接读缓存；就算关闭缓存，在同一张截图上重复问，结果也基本一样。改为：**关闭缓存**，在 3 种页面变体下各定位一次：原样、`attr`（去掉测试标记）、`style`（换样式），复用现有的变更注入；每次比较定位到的中心点是否落在该元素的 bbox 内。这样得到 0–3 分；低于 3 分的标为“疑难控件”，必须带上选择器；
4. 结果写入知识库，置信度分为三档：已验证 / 未验证 / 人工确认。

**成本**：每个控件 1 次标注加 3 次定位，共 4 次视觉模型调用。演示站约几十个控件，按当前模型价格算花费不大，但开跑前要按实际控件数和模型单价估算，**先告诉用户**。

**代码上的准备**：执行器里的 `AiAgent` 接口目前只有 `aiAct / aiAssert / aiQuery`。M2 要加 `aiLocate`，测试里的假 Agent 也要同步加上。

### 3.4 数据模型（SQLite，新表）

| 表 | 主要字段 |
|---|---|
| `kb_runs` | 探索批次：目标（环境 id 或基础 URL）、配置、开始结束时间、状态数、元素数、被拦截的请求数、token、模型名 |
| `kb_states` | id、run_id、url_pattern、fingerprint、截图、标题摘要、reproducible、first_seen |
| `kb_elements` | id、run_id、**element_key**（role + 名称 + 所在区域，用来把导航栏这类每页都有的控件合并成一条）、selector（首选 data-test / role，其次 CSS）、function_desc、midscene_desc、locate_stability（0–3）、verified、hard_case、danger（none / keyword / model / write_request）、updated_at |
| `kb_occurrences` | element_id、state_id、bbox、截图裁切路径（同一控件出现在多个页面时，位置和截图按页面分别存） |
| `kb_transitions` | from_state、element_id、action（click / fill / select）、to_state、effect_desc、verified |
| `kb_flows` | id、name（如“登录后播放视频”）、state/element 路径、来源（自动归纳 / 人工） |

截图裁切存在 artifacts 目录，和运行截图走同样的清理策略，避免占满小内存 VPS 的磁盘。

### 3.5 使用知识库（M3、M4）

- **执行时**：Midscene 1.17 提供了 `setAIContext('aiAct', ...)`，可以在每一步执行前设置背景描述。做法是：按当前页面的状态（URL 模板）筛出这个页面上的控件，再按步骤文本做关键词匹配，取前几条的 midscene_desc 和功能说明作为背景描述。**第一版不做向量检索**：一个系统的控件通常只有几十到几百个，先按页面筛选再做关键词匹配就够了；引入向量模型会增加依赖和内存，1GB 的服务器也承受不了。等实验数据证明关键词匹配不够用，再考虑；
- **疑难控件走选择器**：一条自然语言操作可能包含好几个动作（“输入用户名密码并点击登录”），没法把整条换成一个选择器。所以这一条只用在“只操作一个控件”的步骤上，而且**复用现有结构**：执行器已经支持“代码步骤失败时由 AI 兜底”（step.fallback，结果记为 healed）。用例生成时，碰到疑难控件就直接生成“代码步骤（选择器）+ AI 兜底（midscene_desc）”，**不在执行器里另做一套 AI 失败后退回选择器的逻辑**；
- **回写**：兜底发生时（healed），把这个控件的稳定性评分降低，并在知识库页面上提示“选择器可能已失效”。回写只改评分和提示，不自动改用例；
- **用例生成**：用例工坊生成时，把知识库和流程地图作为上下文，要求只引用知识库里已验证的控件描述。这要新建一个 Prompt 版本（例如 `gen-kb-v1`），不能和根据 v1 废弃原因改出来的 `gen-v2` 混在一起，否则对比时分不清采纳率的变化是哪个改动带来的；
- **界面**：知识库页面按页面分组展示控件卡片（截图裁切 + 描述 + 稳定性评分 + 危险标记）；转移图做可视化；可以人工修正；访客只读。

## 4. 评估方案（这是亮点，必须做）

**实验对象**：只在本仓库自带的演示站（`/demo/`，TodoLite）上做，**不用公开的第三方站点**（包括 TodoMVC 官网），避免在没有授权的系统上自动点击。演示站上目前没有纯图标控件，要先加上播放、收藏这类控件，才能测知识库对“认不出图标”是否有用。**这些疑难控件是作者自己加的**，结果里必须写明这一点，并且在跑实验前先把控件清单和预期写进 `docs/explore-results.md`，不能看到结果再挑控件。

**第二个被测对象（M4 前评估选型）**：演示站太简单，只用它得出的结论说服力有限。计划在本机用 Docker 部署一个开源的、更复杂的 Web 应用当被测对象。自己部署的实例算有授权，但不连外网的第三方服务。选型要求：许可证是 MIT 或 Apache 2.0；自带图标按钮和多页面业务流程（例如开源电商或媒体类项目）；镜像加数据库能在本机正常运行（实验在本机跑，不放到 1GB 的演示站服务器上）；能用种子数据一键重置，保证每轮实验的初始状态一致。选型结果和不选其他候选的理由写进本文档。这一项不影响 M1–M3。

| 实验 | 对照组 | 实验组 | 指标 |
|---|---|---|---|
| A. 执行成功率 | 纯 Midscene 自然语言 | 同一份步骤文本 + 知识库背景描述（疑难控件用“选择器 + AI 兜底”） | 步骤成功率、用例通过率、95% 置信区间（Wilson） |
| B. 成本 | 同上 | 同上 | 每条用例的 token、耗时、模型调用次数 |
| C. 稳健性 | 同上 | 同上 | 用已有的变更注入（attr、style）后的存活率 |
| D. 编写效率 | 用例工坊 + 不带知识库的 Prompt | 用例工坊 + 带知识库的 Prompt（`gen-kb-v1`） | 采纳率、平均修改步数（复用工坊度量；同一需求、同一模型） |
| E. 探索质量 | — | — | 控件覆盖率（与人工列出的控件清单对比）、功能标注准确率（全部人工检查；演示站控件不到 50 个，不抽样）、转移验证通过率 |

**控制变量**：
- 两组都**关闭 Midscene 缓存**，否则第二次以后跑的是缓存，量的不是模型的定位能力；
- 两组用同一个模型、同一份步骤文本，执行顺序交替进行；
- 每条用例每组至少重复跑 5 次，总样本量写进结果；样本太少时，置信区间会很宽，照实写“差异不显著”。

**要求**：结果如实记录在 `docs/explore-results.md`，包括失败案例和知识库反而拖后腿的情况。比如背景描述太长导致模型分心、token 增加但成功率没提高，也要写进去。大规模实验跑之前，先按“用例数 × 重复次数 × 平均每次 token × 单价”估算费用，告诉用户，用户同意后再跑。

## 5. 分阶段计划

| 阶段 | 内容 | 验收 |
|---|---|---|
| M1 | 探索器 + 两层安全边界 + 状态去重 + 敏感信息不落盘；只采集、不标注、不调用模型 | 夹具页面上的测试证明：危险按钮没被点、写请求没发出、没访问白名单外的地址；演示站能自动跑完，状态数稳定 |
| M2 | 大模型标注 + 点击验证 + 变更注入下的定位稳定性检查；知识库表和页面 | 演示站控件全部入库并带评分；开跑前先报费用 |
| M3 | 执行时注入背景描述 + 疑难控件生成“选择器 + AI 兜底”步骤 + 兜底后回写评分 | 实验 A、B 有数据 |
| M4 | 状态转移图可视化 + 流程归纳 + 用例工坊接入（`gen-kb-v1`） | 实验 C、D、E 有数据 |

每个里程碑单独提交，测试先行；M1 完全不调用模型，可以先在 CI 里跑通。

## 6. 非目标

- 不做对第三方系统的逆向破解，只在授权的测试环境上运行；
- 不承诺“完全不需要人工”：知识库里的“人工确认”是设计的一部分；
- 第一版不做向量检索、不支持多标签页和 iframe 内的探索、不处理验证码；
- 不涉及任何实习单位的系统和数据。实习中的同类实践只在面试里讲思路，不用公司内容。

## 7. 审阅记录（v1 → v2）

对照现有代码（`server/runner/ai.ts`、`executor.ts` 的 AI 兜底、`mutations.ts`、`server/access.ts`、用例工坊）审阅 v1 草案，发现以下问题并已修改：

| # | v1 的写法 | 问题 | v2 的改法 |
|---|---|---|---|
| 1 | 危险动作靠关键词加大模型判断识别 | M1 不调用模型，只剩关键词，名字普通的按钮照样会写数据；识别错一次就是真的删了数据 | 加网络层拦截：非 GET 请求默认取消、白名单外的域名不访问；关键词只是第一层 |
| 2 | 用 `aiLocate` 定位 3 次看是否一致 | 开缓存时后两次读缓存；同一截图上重复问结果也基本一样，测不出不稳定 | 关闭缓存，在原样 / 去掉测试标记 / 换样式 3 种变体下各定位一次，复用变更注入 |
| 3 | AI 定位失败时从知识库取选择器兜底，执行器新增一套逻辑 | 现有执行器已经有反方向的结构（代码步骤失败 → AI 兜底）；一条自然语言操作常包含多个动作，没法整条换成一个选择器 | 疑难控件直接生成“代码步骤 + AI 兜底”，复用 step.fallback 和 healed 状态 |
| 4 | 关键词 + 向量混合检索，复用另一个项目的 RAG | 一个系统的控件不多；向量模型增加依赖和内存，1GB 服务器承受不了；另一个项目的代码也不在本仓库 | 先按当前页面筛选，再按关键词匹配；用 `setAIContext('aiAct', ...)` 逐步注入 |
| 5 | 复用现有脱敏逻辑 | 仓库里没有通用脱敏逻辑 | M1 新增：密码框的值、Authorization、Cookie 不记录 |
| 6 | 状态 = URL 模板 + role/name 指纹 | role/name 里带有数据（待办内容、视频标题），列表一变就是新状态 | 合并重复的兄弟元素，名称里的数字归一化；没写怎么回到某个状态，补了“从起点重放路径” |
| 7 | `kb_elements` 挂在 state 下 | 导航栏这类控件每个页面都有，会重复标注、重复花 token | 拆成 `kb_elements`（按 element_key 合并）和 `kb_occurrences` |
| 8 | 在演示站和 TodoMVC 上评估 | TodoMVC 是第三方站点，不在授权范围内；演示站没有纯图标控件，测不到要解决的核心问题 | 只用本仓库的演示站，先加图标控件并写明是自己加的；预期先写下来 |
| 9 | 实验没写缓存、重复次数 | 缓存会让后面的运行不再调用模型；单次运行的差异没有意义 | 两组都关缓存、交替执行、每组至少 5 次，写明样本量 |
| 10 | 用例工坊接入知识库，没说 Prompt 版本 | 和计划中的 `gen-v2` 混在一起，采纳率变化分不清是哪个改动带来的 | 单独建 `gen-kb-v1`，和不带知识库的同版本对比 |
| 11 | 标注准确率人工抽查 50 条 | 演示站控件不到 50 个 | 全部人工检查 |
| 12 | 没提部署限制和访客权限 | 探索要开浏览器，演示站 1 核 1GB；访客触发探索会消耗 token | 和用例运行共用一个执行队列；访客不能发起探索，补测试 |

## 8. M1 实现记录（2026-11-06）

已实现：`server/explore/`（安全判定、状态指纹、探索器）、`server/explore-routes.ts`（`POST /api/explore`、`GET /api/explore/runs[/:id]`）、`kb_*` 表。没有界面（M2 与知识库页面一起做），目前通过接口使用。

**与设计的差异和已知限制**
- 请求体必须带 `authorized: true`，否则返回 400；默认只放行 `baseUrl` 所在的主机；探索期间有用例在跑时返回 409。
- 预置登录动作（`setup`）里的值不落盘，库里记录为 `***`；密码框一律不填写。
- 状态指纹只看**可交互元素**。点“登录”后出现的错误提示不是可交互元素，所以记为“无变化”（`no_change`）。M2 加视觉标注后再补文本变化。
- 列表项的合并只看标签（`li` / `tr` / `article` 等）。第一版试过把 class 也算进结构，结果待办项勾选后 class 变成 `done`，被当成新结构，导致同一个复选框重复记录、状态不可复现。已改，并在演示站上重跑确认。
- 拦截层只覆盖 HTTP 请求。WebSocket、WebRTC 不在拦截范围内，所以不适合探索依赖它们的系统。

**M1 在演示站上的实测**（本机，2026-11-06）
- 登录后探索：1 个状态、5 个控件、3 次点击；“退出登录”“删除”被识别为危险，只记录、没有点击；没有请求被拦截。
- 不登录探索：1 个状态（登录页）、3 个控件、2 次点击。
- 演示站只有登录页和待办页两个页面，所以状态很少。能证明危险动作不会被点击的是夹具页面上的测试（`tests/unit/explore.test.ts`），不是演示站的结果。
