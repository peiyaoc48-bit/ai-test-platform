# 面试怎么讲：AI 驱动的 UI 自动化测试平台

> 写给自己看的讲稿。每个结论都能在仓库里找到对应代码或测试，被追问时可以直接打开给面试官看。

## 一、30 秒版本

> 我做了一个测试平台，用例可以用三种方式写：Playwright 选择器代码、自然语言（交给 Midscene 视觉模型执行）、接口请求（YAML 描述），三种步骤可以混在同一个用例里。平台负责异步执行、逐步截图、统计模型的 token 消耗；支持多环境、用例集、JUnit 和 CI，也能把用例导出成独立的 Playwright 脚本。比较有特色的是把我毕设里“选择器 vs 视觉断言”的对比实验做成了功能：一键在去掉测试标记、换样式的情况下重跑用例，对比哪些步骤失效，选择器失效时还可以由 AI 兜底自愈。我还用它测了自己的毕设系统。最近又加了“用例工坊”：AI 生成的用例必须逐条审核才入库，平台统计采纳率、对比 Prompt 版本，并用需求覆盖矩阵看需求测全了没有。平台自己有三层测试：171 条单元 / 集成测试、100 条 Python 接口自动化、16 条 Playwright E2E。

## 二、架构（画在白板上）

```
浏览器（Vue） ──轮询──▶ Fastify REST API ──▶ SQLite
                              │
                              ▼ enqueue
                     Executor（串行队列）
              ┌───────────────┼────────────────┐
        Playwright 代码   Midscene 视觉模型    接口步骤（fetch）
              └───────────────┴────────────────┘
                              ▼
                演示站点 /demo + 后端 /demo-api
CI：ci-run 脚本 ─触发用例集─▶ API ─轮询─▶ JUnit XML、退出码
```

要点：
- **为什么异步**：一次运行要几秒到几分钟（视觉模型慢），HTTP 请求不能一直挂着，所以提交返回 202 和 runId，前端轮询。
- **为什么每步都写库**：前端轮询就能看到实时进度；进程崩了，也能知道停在哪一步（重启时会把中断的运行标记为“异常”）。
- **浏览器按需启动**：纯接口用例不打开浏览器，6 个接口步骤总共约 20ms。

## 三、接口测试知识点（对照代码复习）

| 知识点 | 在项目里的位置 | 一句话 |
|---|---|---|
| 状态码语义 | `server/app.ts` | 新建 201，异步受理 202，删除 204，参数错误 400，未登录 401，不存在 404 |
| 鉴权 / token | `server/demo-api.ts` | 登录发放 token，后续请求带 `Authorization: Bearer <token>`；token 无效或已退出都返回 401 |
| 接口关联 | 接口步骤的 `extract`，pytest 的 `auth` 夹具 | 上一个接口的返回值（token、id）作为下一个接口的入参，和 JMeter 里的“关联”是一回事 |
| 参数校验与边界值 | `api-tests/data/*.yaml` | 空值、类型错误、超长；边界值 100 字符可以、101 不行，50 步可以、51 步不行 |
| 契约测试 | `api-tests/common/schemas.py` | 用 JSON Schema 校验字段和类型，前后端字段改名会第一时间发现 |
| 异步接口怎么测 | `client.wait_run` | 提交 → 轮询到终态（有超时），不用固定的 `sleep` |
| 测试数据准备与清理 | `conftest.py` 的 `case_factory` | 用例里造的数据在用例结束后自动删除；共享环境里的统计用“前后增量”断言 |
| 数据隔离 | `test_sessions_are_isolated` | 每个 token 一份独立数据，用例之间互不影响，也就能并发执行 |
| 幂等 | `test_case_lifecycle` | 重复删除返回 404，不会误删别的数据 |
| 安全 | 报告里的鉴权头脱敏 | token 只显示前 12 位，避免泄露在报告里 |

## 四、常见追问

**1. 视觉断言这么方便，为什么不全用它？**
我在毕设里做过对比实验：删掉测试标记后，视觉断言 100% 通过、选择器只剩 40%；但单个视觉断言慢约 200 倍，每次约 8500 token。所以平台的策略是：操作和造数据用选择器或接口（快、确定），“看起来对不对”这类检查用视觉断言，稳定后再沉淀成脚本。报告里逐步显示 token，就是判断哪些步骤值得沉淀的依据。

**2. token 怎么统计到每一步？**
Midscene Agent 的 `metrics` 是累计值，执行器在每一步前后各取一次，差值就是这一步的调用次数和 token（`server/runner/executor.ts`）。

**3. 没有模型 key 时怎么办？**
自然语言步骤标记为“跳过”而不是“失败”，代码和接口步骤照常执行。这样不会因为环境缺少 key 把流水线标红；全部步骤都被跳过的运行不计入通过率。

**4. 测试怎么保证稳定、不 flaky？**
- 用 Playwright 的自动等待和 `expect` 重试，不写固定的 `sleep`；异步接口轮询时带超时。
- E2E 起两个互相隔离的平台实例，各用一个临时数据目录；接口测试自己启动一个临时实例。
- 共享环境里不依赖已有数据：自己造数据并清理，统计用增量断言。

**5. 怎么接入 CI？**
`scripts/ci-run.ts` 触发用例集、轮询到结束，打印汇总并写出 JUnit XML，有失败时以退出码 1 结束让流水线变红。GitHub Actions 依次跑类型检查、单元测试、E2E、pytest，最后启动平台执行“冒烟”用例集，并上传所有报告。

**6. 平台本身是怎么测的？（测试金字塔）**
底层 171 条 vitest（纯逻辑 + 真实 Fastify / SQLite / Chrome 的集成测试，用假 Agent 代替模型），中间 100 条 pytest 接口测试，顶层 16 条 Playwright E2E（含本地假模型验证 AI 生成和用例工坊流程）。越往上越慢、越少。

**7. 代码步骤直接在服务端执行，安全吗？**
不安全，这是有意识的取舍：只适合内网的可信用户。要对外开放，需要把执行器放进独立的容器或 worker 中隔离，并限制网络和文件系统访问。README 里写明了这一点。

**8. 想支持并发执行，要改哪里？**
现在是一个浏览器、一个串行队列，每次运行用一个独立的 BrowserContext。改成 worker 池，每个 worker 一个 context，加并发上限即可。数据层面每次运行本来就互相隔离，演示后端也按 token 隔离数据。

**9. 开发中遇到过什么问题？**（都是真实发生的）
- **编辑页数据被覆盖**：E2E 发现，进入编辑页后立即修改名称，保存的还是旧名字。原因是异步加载的用例数据晚于用户输入到达，把输入覆盖了。修复方法是数据加载完成前不渲染表单。
- **Playwright 的 `getByTestId` 找不到元素**：它默认找的是 `data-testid` 属性，而项目用的是 `data-test`，需要配置 `testIdAttribute`。
- **校验顺序变化导致测试失败**：支持“纯接口用例可以不填 URL”后，校验改成先看步骤再看 URL，原来断言错误信息里包含“URL”的测试就失败了。这说明错误信息也是接口契约的一部分，改动时要同步更新测试。

**10. 这个平台和你在爱奇艺用的框架是什么关系？**
实习时和带教聊到自动化用例，接触到“自然语言用例 + 大模型 + 视觉执行”的思路，下班后自己从零做了一个通用版本。用的是开源的 Midscene、Playwright 和自己写的演示站点，没有用公司的代码和内部模型。公司框架只讲思路层面，不讲内部实现。

**11. 你用这个平台测过真实系统吗？**
测过我的毕设“在线考试智能监考系统”（`examples/proctor`）。配了一个环境：Chrome 启动参数用一段无人画面视频模拟摄像头，授予摄像头权限，预置“已同意协议”的 localStorage，超时调到 90 秒。写了三个用例：
- 8 步接口业务链路：教师建考 → 考生开考 → 上报“人脸消失” → 交卷 → 教师查报告并复核，用 `extract` 串起 token、考试 id、会话 id、事件 id
- 7 步鉴权与越权：未登录 401、考生建考 403、边界值 400
- 一个模拟摄像头的 UI 用例

在我本机的一次运行中三条都通过：接口用例各 0.3 ~ 0.4 秒，UI 用例约 16 秒。

**12. 鲁棒性对比和自愈是怎么实现的？**
用 `context.addInitScript` 在页面脚本执行前注入：一种用 MutationObserver 持续去掉 `data-test` 等属性，另一种追加一段 CSS 换掉颜色、字号和圆角，不改被测系统。同一用例以“失败后继续执行”的模式在三种变更下各跑一次，前端把结果排成矩阵。自愈是给代码步骤加一句兜底描述：代码失败后改调 `aiAct` / `aiAssert`，通过就记为“已自愈”，不记为普通的通过，提醒维护者修选择器。

**13. 导出脚本有什么用？**
平台适合探索和管理，长期稳定的用例更适合进代码仓库跟着 CI 跑。导出时，接口步骤翻译成 Playwright 的 `request` 加 `expect`，环境配置转成 `test.use`。导出时踩过一个坑：先整体转义再替换占位符，会把 `{{$timestamp}}` 里的 `$` 也转义掉，导致注册的用户名变成固定字符串。后来改成只转义字面量部分，并在集成测试里真实运行导出的文件来防止回归。

**14. 不稳定用例怎么识别？界面为什么这样设计？**
参考 Allure TestOps：取每个用例最近 10 次有结论的运行（排除跳过和变更注入），统计“通过 ↔ 失败”的切换次数。个人项目运行次数少，阈值取 2（Allure 默认是 3）。只看失败率分辨不出“一直失败”和“时好时坏”，前者通常是真缺陷，后者才是不稳定，所以要看切换次数。运行详情参考 Playwright Trace Viewer：左边是步骤时间线，右边是选中步骤的详情，打开时自动定位到失败的那一步，排查时不用在长页面里滚动查找。

**15. 用例工坊是什么？为什么不直接“AI 生成用例”就完了？**
AI 生成本身不难，难的是回答“生成的东西有多少能用”和“需求测全了没有”。所以我把它做成一条流水线：需求文档先由模型拆成需求点，每个点必须带原文摘录，平台检查摘录能不能在原文里找到，找不到就标红（便宜的幻觉检查）；然后按批次生成，每批记录模型、Prompt 版本和输入指纹；草稿要人逐条判定通过 / 修改 / 废弃，废弃必须选原因。这样就能算采纳率、修改量和废弃原因分布，再拿两版 Prompt 在同一批需求点上对比。
- 追问“样本这么少，比较有意义吗”：一批二三十条，所以采纳率给 Wilson 置信区间，两批差异用 Fisher 精确检验，每组少于 20 条时页面直接提示“仅供参考”。这套做法沿用了我字幕翻译评测项目里的思路。
- 追问“覆盖矩阵怎么判定”：区分“已关联”和“已验证”。关联只说明有用例声称覆盖了这个需求点，验证要求关联用例最近一次正常运行通过。这一点参考了开源项目 SoftJL 的说法：coverage link 不等于 passed test。
- 追问“需求改了怎么办”：重新解析时新旧需求点按标题相似度一一匹配，匹配上的沿用编号和用例关联，所以覆盖矩阵不会因为重新解析整体错乱；编号不复用。
- 踩过的坑：接口测试发现非法的 Prompt 版本号返回了 502（当成了模型调用失败），实际应该是参数错误 400；版本号来自请求参数，还要限制成 `vN` 防止拼出目录外的路径。

## 五、简历写法参考（数字均来自仓库）

- **平台搭建**：基于 Node + TypeScript（Fastify）+ Vue 3 + SQLite 从 0 实现用例管理、异步执行、测试报告、AI 生成用例；步骤支持自然语言（Midscene）、Playwright 代码与接口请求混写。
- **接口测试与 CI**：接口步骤用 YAML 描述请求、断言和变量提取（接口关联），纯接口用例不启动浏览器；支持用例集批量运行、导出 JUnit，CI 脚本在有失败时以非 0 退出，并接入 GitHub Actions。
- **鲁棒性与自愈**：把毕设中“选择器 vs 视觉断言”的对比实验产品化：注入“去掉测试标记 / 更换视觉样式”的界面变更，一键对比每一步的存活率；选择器失效时可由视觉模型兜底（自愈）并提示更新。
- **实战**：用平台测试毕设监考系统：多环境配置（模拟摄像头、权限、预置登录态），8 步接口业务链路（教师 / 考生双角色，token 关联）、越权与边界校验，以及摄像头场景的 UI 用例。
- **用例工坊**：设计 AI 生成用例的审核与度量流程：需求解析为带原文出处的需求点 → 按批次生成 → 逐条审核留痕；以采纳率（置信区间）、废弃原因、生成即跑通率评估生成质量并对比 Prompt 版本；需求覆盖矩阵区分“已关联”和“已验证”，对缺口定向补生成。（采纳率等数字待真实数据实测后再写）
- **质量保障**：搭建 pytest + requests 接口自动化框架（JSON Schema 契约、YAML 数据驱动、夹具自动造数和清理），100 条接口用例；另有 171 条单元 / 集成测试和 16 条 Playwright E2E。
